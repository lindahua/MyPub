# Author profile enrichment plan

## Goal and current state

Attach a confirmed Google Scholar profile ID and/or ORCID to each author identity where public evidence supports the match. Neither identifier is required for an author to remain valid. This plan covers the private catalog configured at `~/Data/MyPubRepo`; it does not change publication credits or merge author identities as a side effect.

Inventory on 27 September 2026: 1,852 author records (1,850 active, two merged), 833 publications, one author with a Scholar ID, one with an ORCID, and six active same-name groups. The owner, Dahua Lin, directly supplied ORCID `0000-0002-8865-7896`; it is attached to the same author record as Scholar ID `GMzzRRUAAAAJ`. Of 1,837 authors linked to at least one publication, 1,199 have at least two linked publications, 344 have at least five, and 134 have at least ten. Seven publication credits remain unlinked. These counts are a baseline, not a claim that all authors have public profiles.

## Existing format and update path

Schema version 2 already has `author.identifiers.google_scholar` and `author.identifiers.orcid`; no schema change is needed. Store the Scholar profile's case-preserved `user` query value and the normalized, checksummed ORCID (for example `0000-0002-1825-0097`). Keep evidence and review state out of the identifier fields. The core validates uniqueness across non-merged identities and normalizes URL-form input. Apply accepted patches through `mypub author update AUTHOR_KEY --json-file PATCH.json --expected-revision REVISION` or the corresponding core operation, then run catalog validation. The update patch's `identifiers` object replaces that object, so every patch must carry forward an existing identifier on the same author.

## Workflow

1. **Build a reproducible candidate inventory.** Export active author UUID, key, names and aliases, current identifiers, linked publication titles, years, DOIs, venue, and coauthors. Flag identical or similar names, overlapping aliases, unlinked credits, archived identities, and conflicting existing IDs. Prioritize the 134 authors with at least ten linked publications, then the rest with repeated publications, then single-publication authors. Keep candidate and evidence files in an ignored local work area until reviewed; do not add unverified URLs to canonical JSON.
2. **Discover ORCID candidates.** Start with ORCID IDs explicitly given on a matching publisher paper, institutional page, personal homepage, or another authoritative author-controlled page. Search the public ORCID registry using name variants and, when available, known affiliation and DOI. Read each candidate's public record and compare works (prefer exact DOI), research area, affiliations over time, and other linked sites. The ORCID public API supports public record search and reads, but ORCID discourages assigning an ID from a name search alone. Avoid assuming a missing public work or affiliation disproves a match; record visibility may be limited. [ORCID public API](https://info.orcid.org/what-is-orcid/services/public-api/), [ORCID registry search guidance](https://info.orcid.org/what-is-orcid/services/public-api/searching-the-registry/)
3. **Discover Scholar candidates.** Search by name variants plus distinctive publication titles, coauthors, or institutional context. Capture only the public profile `user` ID. Verify the profile against at least one distinctive catalog publication and additional independent context such as another work, an affiliation, a personal site, or an ORCID cross-link. A Scholar search result, citation page, or shared name alone is insufficient. A profile may be private or absent; leave the field empty in that case. [Google Scholar profile URL and visibility guidance](https://scholar.google.com/intl/en/scholar/citations.html)
4. **Score and review each candidate separately by provider.** A proposed match must have a direct profile URL, retrieval date, evidence URLs, catalog author UUID, matched publication UUIDs/DOIs, and any contradictory evidence. Treat exact DOI overlap plus consistent name/coauthors as strong evidence; multiple distinctive title overlaps or an explicit author-controlled cross-link can also support acceptance. Affiliation and topic alone are supporting context. For common names, identical names, sparse profiles, competing candidates, or conflicting publication histories, require manual review; do not choose the highest search rank or score automatically. A negative decision should retain its reason in the work queue so the same false candidate is not repeatedly proposed.
5. **Apply accepted assignments in small batches.** Re-read the author record immediately before each update, preserve existing fields and identifiers, and check that the candidate ID is not already assigned to another retained identity. Normalize IDs and use the CLI/core transaction and revision check. Before bulk updates, add a workflow that saves source URLs and the reviewer decision as an existing-schema catalog review in the same transaction as the author patch; the current `author update` command alone does not do this. Resolve any collision by investigating the two author identities; never silently merge them or overwrite an identifier. Keep Scholar and ORCID decisions independent: one can be accepted while the other remains unknown.
6. **Verify and report coverage.** After each batch, run `mypub validate`, check uniqueness and profile URLs, and sample both accepted matches and rejected ambiguous cases against the source pages. Report authors with Scholar, ORCID, both, neither, ambiguous candidates, and source-unavailable cases, separately for active and merged identities. List every changed author key and its evidence. Stop a source-specific discovery pass on access blocks or rate limits and resume later without treating unsearched authors as profile-free.

## Matching guardrails

- The catalog UUID identifies the person; name equality does not. Preserve separate identities for the six same-name groups unless independent evidence supports a deliberate merge.
- Compare a candidate with the **linked publication set of that author UUID**, not all catalog papers that print the same name. Review potentially incorrect author-credit links before using them as match evidence.
- A publication DOI tied to a candidate profile must identify the same bibliographic work and author, not merely another version or a same-name contributor.
- Multiple legitimate profiles for one person can use `identifier_aliases` after confirmation. A mistaken assignment must be removed, not stored as an alias.
- No-match and uncertain results remain empty identifiers. Do not create placeholder IDs or infer an ORCID from checksum-valid syntax alone.

## Implementation sequence

The first deliverable is an inventory and review queue generator using read-only catalog access, with candidate discovery from public sources and explicit evidence fields. Trial it on the owner, the six same-name groups, and a small set of high-publication coauthors. Review errors and adjust matching rules before expanding. Then process authors in resumable batches and apply only reviewed assignments. A final coverage report should distinguish verified profiles from unresolved and unsearched authors. This enrichment uses the existing author schema and CLI; any new automation should remain a separate workflow, not part of routine publication imports or Scholar citation mirroring.

### Remaining queue

1. Review the unassigned Crossref and OpenAlex candidates, especially conflicting candidates and the six same-name groups. The cached public ORCID records and source responses avoid repeat requests. A failed public-work match is inconclusive because ORCID works can be private or incomplete.
2. Continue author-controlled homepage and institutional-page discovery for frequent coauthors lacking Scholar IDs, then work down to authors with fewer catalog publications. Search for distinctive papers and coauthors as well as names. Leave a field empty when the public profile cannot be established.
3. Revisit the two failed ORCID fetches and source 404s only if new evidence appears. Refresh source caches when publisher metadata or author profiles change, rather than assuming the current snapshot is exhaustive.
4. Validate after every new batch, report active/merged coverage separately, and resolve the seven unlinked publication credits as a separate identity-cleanup task before using them as profile evidence.

The 1,714 blank pairs are a mixture of unsearched authors, authors with no public profile, and unresolved identity matches; they are not negative determinations. No bulk Google Scholar scraping was performed.
